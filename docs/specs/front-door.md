# The front door: the analysis app, served by the device

**Goal.** `https://xtape.local` is the one address. With a card in the player it shows the
**Player view**; with the card out it shows the **Prepare view** — the analysis page that
measures the card and writes `xtape.db` back to it. The app's own code ships in the firmware;
the 38 MB of models and runtimes are fetched once and cached on the computer that runs it.

The decision, its evidence and its rejected alternatives are
[ADR 0048](../adr/0048-the-device-serves-the-analysis-app.md). Vocabulary is
[`CONTEXT.md`](./CONTEXT.md): **Front door**, **Player view**, **Prepare view**, **Card state**,
**Shell**, **Weights**.

**Status:** built and running on the board. `https://xtape.local/` serves the Shell from its own
flash over TLS, `/api/status` answers, `/library` is the index, and `http://xtape.local/stream`
is plain on port 80. What is **not** proven: no browser on this machine has trusted the
certificate, so the directory picker and the service worker have not run on the device's own
origin (the TLS was exercised with `curl --cacert tls/ca.pem`); the Player view is a
placeholder; and the §9 measurements are unmeasured. The Shell is 816 KiB, not the 0.47 MB
estimate of §1.

---

## 1. What is served, and from where

| Piece | Bytes | Lives |
|---|---:|---|
| `index.html`, app bundle, worker, `wasi-adapter`, `ort.mjs`, `sw.js`, manifest, icons, `shell.json`, `weights.lock.json` | **816 KiB** | 1 MB SPIFFS partition at `0x610000` |
| Essentia (`essentia-wasm.es.js`, 2.56 MB) | 2.6 MB | jsDelivr, pinned tag, sha256-checked |
| TagLib's one browser wasm | 0.7 MB | jsDelivr |
| ONNX Runtime wasm | 14 MB | jsDelivr |
| Models, nine of them | 23.9 MB | jsDelivr |
| **Weights together** | **≈ 41 MB** | fetched once, cached |

**F1.** `web/dist-shell` is packed by `spiffs_create_partition_image` into the `frontdoor`
partition, so `idf.py flash` writes the firmware and the page together, and the build logs the
app commit it packed. The pack is a **configure-time** decision: after building the Shell the
build directory must be reconfigured. A clean checkout without a Shell still builds — the device
is useful without a page, with `/` answering `503` naming `/library` — and a build that is
meant to ship one passes `-DXTAPE_REQUIRE_SHELL=1`, which turns a missing or empty Shell into a
configure error.

**F2.** The **Shell** is our code and nothing else. The worker is built with Essentia
external: it loads the module from the CDN, not from the bundle.

**F3.** The **Weights** are pinned to a tag and verified against the manifest's `sha256`
before use. JavaScript modules are fetched as text, checked, and imported from a blob URL;
`ArrayBuffer` artefacts are checked before they reach ONNX Runtime. Verification happens on
every cold load, not only the first.

## 2. Origins and routes

**R1.** `https://xtape.local` (port 443) serves the app at `/`, the JSON API at `/api/*`, MCP at
`/mcp`, and the index at `/library`. Unknown paths are `404`: the page is one screen with no
client-side routes, so there is nothing for a fallback to serve.

**R2.** `http://xtape.local` (port 80) serves `/stream`, plain and unchanging, and answers every
other path with `301` to the same path on HTTPS. No TLS on 80, ever: hardware players and car
head units cannot trust a private CA.

**R3.** `/` stops being the index. The index moves to `/library` unchanged — the diagnostic
that needs no JavaScript and no certificate.

**T1.** TLS is `esp_https_server`, behind the existing `http_server.h` public API. The device
serves the **shipped** certificate and key for `xtape.local`, compiled in from a checked-in pair
under `tls/` — the same pair in every image, signed once by a CA whose key stays offline. The
device needs no clock: the client validates the dates.

**T1a.** The user trusts the shipped certificate **once** per client; nothing is generated by
anyone who installs the firmware:

```sh
security add-trusted-cert -d -r trustRoot \
  -k "$HOME/Library/Keychains/login.keychain-db" tls/ca.pem
```

Whether that trust is granted to the leaf directly or to the CA that signed it is decided by an
experiment (`§9.6`). The leaf carries three names — `xtape.local`, `localhost`, `127.0.0.1` —
so trusting it directly bounds the trust to those, not to one.

**T2.** Two listeners, one per port, each with its own handle table, and a route names the one
it belongs to. As built, the TLS listener is `esp_https_server` with one catch-all URI that
dispatches into the shared route table, and the plain listener is the hand-written loop the host
tier still uses — because `/stream` returns `HTTP_UPGRADED` and its sender owns the fd for the
length of a listen, which `httpd` cannot express (it replies and closes when a handler returns,
and lwIP has no `dup()`).

**T3.** The host tier keeps the hand-written loop as the other backend of the same
`http_server.h`, so the route handlers and the integration checks are shared. TLS and keep-alive
are board-only behaviour and are not asserted by the host suite.

## 3. The page

**P1.** A service worker precaches the Shell on install, so the app opens with the device
switched off. It opens in the **Prepare view** and stays there: a cold offline load has no
status, and a missing device reads as "no card", not as an error banner.

**P2.** The Weights are cache-first, in a cache whose name carries the app version and the
manifest hash. A model swapped at the same URL is a cache miss, not a stale hit.

**P3.** `index.html` and `sw.js` are served `no-cache`; hashed `assets/*` are
`public, max-age=31536000, immutable`; anything else is revalidated. One `Cache-Control` per
response — `http_send_headers` defaults to `no-cache` and a route's own header replaces it, never
joins it. `/api/status` is `no-store`; the rest of `/api/*` keeps the default `no-cache`, which
revalidates the library views and the control commands.

**P4.** The page is installable: a manifest with the product's name and icons, served from the
same partition.

**P5.** An update is never imposed: a new service worker waits rather than replacing the page
under a running analysis. Offering it — a button that reloads — is **not built**.

## 4. The two views

**S1.** `GET /api/status` returns the **Card state**, the library's track count and generation,
and what the broadcast is playing: `title`, `path`, `elapsed_ms`, `duration_ms`. The page polls
it every 5 s and maps the two times to `elapsed`/`duration` for the view. It is `no-store`, and
it answers only on its own path: `/api/statuses` is a 404.

**S2.** Card in → **Player view**. Card out → **Prepare view**. The view is chosen by the Card
state at load.

**S3.** A change of Card state switches the view only when the queue is idle. Mid-analysis the
page stays and shows a banner offering the switch. A card that comes back does not throw away a
running analysis.

**S4.** The Player view is TBD; until it exists it is a placeholder that says the card is in and
names what is playing, with a link to the stream. The link is absolute and points at port 80,
because the stream is plain HTTP on a different origin from the page.

---

## 5. What this does not change

- The cassette on the panel, the Snapshot flow, the MCP tools and `/api/library`.
- The global premise: the device still serves no Track. The page it serves is not a Track, and
  the card still leaves only as the live stream.
- The host build's composition: it runs the same services, on the hand-written backend.

## 6. Failure modes

| Condition | Behaviour |
|---|---|
| The firmware was built without a Shell | `/` answers `503` naming `/library`; every other route is unchanged |
| `/stream` requested over TLS | `404`: the stream is a plain-listener route, and the TLS listener refuses routes that are not its own |
| The Shell directory exists but has no `index.html` | `/` answers `503` — a page that was packed and is not there is a device fault, not a typo |
| An unregistered `/api/…` path | `404`, never the page |
| The certificate is missing or unreadable | The TLS listener refuses to start; the device still serves the stream on 80 and logs why |
| The client has not trusted the shipped certificate | The browser warns; the page cannot run (no secure context) — the one trust step is documented as the prerequisite |
| CDN unreachable, cache cold | The Prepare view says the analyser cannot start without a first download that needs internet |
| CDN unreachable, cache warm | The app runs from Cache Storage |
| A model's hash does not match | It is refused, named in the log and on the page, and the analysis does not start |
| Card pulled mid-analysis | The queue's current file fails; the page keeps the view and says why |
| Device unreachable on an installed app | The shell opens from cache in the Prepare view; there is no error banner, and a missing device reads as "no card" |

## 7. Build and flash

**B1.** `cd web && npm run build:shell`, then `idf.py build flash` — `build` writes `dist/` for
local development, and `build:shell` writes the `dist-shell/` that is packed. A shipping build
adds `-DXTAPE_REQUIRE_SHELL=1`, which fails the configure when the Shell is missing or empty;
without it the firmware builds and `/` answers `503`.

**B2.** The certificate and key are shipped under `tls/`, produced by `tools/make-cert.sh`, and
compiled in by `components/app/tls_material`. They change only when the pair is rotated, which
re-flashes the firmware — the same thing every other change does.

## 8. Tests

| # | Test | Tier | Status |
|---|---|---|---|
| T1 | The two backends answer the same routes with the same bodies | — | **not testable on the host**: the host compiles only the hand-written backend, and the TLS backend is ESP-IDF-only. What is shared — the route table, the body rules, the status codes — is exercised by the host suite; the TLS dispatch is board-only |
| T2 | `/` serves the app, `/library` serves the index, unknown paths 404 | host | **proven** — `host/tests/front_door_tests.py`, 27 checks |
| T3 | The SPIFFS image holds `index.html`, `sw.js` and the hashed assets, and `sw.js` is served `no-cache` | board | **proven by hand** (three files curled off the board); not automated |
| T4 | A client that trusts the certificate loads the page over HTTPS and reports a secure context | board | **not proven**: `curl --cacert` proves the handshake and the page, but no browser has trusted the certificate, so the secure context itself is unproven |
| T5 | `/stream` is reachable on plain 80 while the app is on 443, and 80 redirects everything else | board | **proven by hand** (`/stream` 200, `/library` 301 to https); not automated |
| T6 | `/api/status` reports the card state within one poll of a removal and a reinsertion | board | **not proven** — the card has not been through a removal/reinsertion cycle since the front door landed |
| T7 | A cold cache loads the weights once; a warm cache starts the analyser with the network off | browser | **not proven in CI**: the web agent's manual Chrome smoke tests passed, nothing automated |
| T8 | A tampered model is refused, by hash | host | **proven at the hash level** (`verifySha256` has accept/reject tests); no test yet that the loader refuses a bad body |

## 9. Open measurements

1. TLS handshake cost and heap on the S3, beside the encoder and the panel.
2. Two listeners' stacks and buffers against the 35 KB of internal RAM that is free during
   playback.
3. First-load time of 38 MB over the LAN, and whether the PWA's cache makes the second load
   invisible.
4. SPIFFS mount time and the read cost of the 816 KiB shell.
5. Whether `showDirectoryPicker` and the service worker behave identically on the device's
   origin as they do on `localhost` — the trust step is the variable.
6. Whether Chrome accepts a **directly-trusted leaf**, so the documented trust step grants one
   name instead of a whole CA. If it does, the CA is never installed anywhere.
